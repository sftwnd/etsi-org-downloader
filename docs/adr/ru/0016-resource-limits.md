# ADR-0016: Ограниченные ресурсы — лимиты контейнера, куча как их доля, выход при OutOfMemoryError

- Статус: Принято
- Дата: 2026-10-30
- Версия на английском: [ADR-0016](../0016-resource-limits.md)

## Контекст

`docker-compose.yml` не задавал лимитов (#58): JVM выбирала размер кучи по памяти виртуальной машины Docker — около
5,9 ГиБ, четверть от 23,7 ГБ, на машине разработчика, — а контейнер мог занять все процессоры. После `OutOfMemoryError`
JVM продолжала работу: ошибка становилась неудачей ресурса, в задаче которого произошла
([ADR-0008](0008-error-isolation-exit-code.md)), хотя любой другой поток мог потерять свою работу.

Память прогона растёт с деревом: посещённые ресурсы ([ADR-0002](0002-link-policy.md)) и future дерева хранятся
до конца. Пробному прогону синтетического дерева из 100 000 файлов понадобилось не больше 124 МБ кучи после сборки,
из 200 000 файлов — 246 МБ, а с кучей 64 МБ и 128 МБ соответственно он завершился ошибкой: около 1,2 КБ на файл.

## Решение

- `docker-compose.yml` ограничивает контейнер: `mem_limit: ${ETSIORG_MEMORY:-1g}` и `cpus: ${ETSIORG_CPUS:-2}`.
- Образ запускает JVM с `-XX:MaxRAMPercentage=75`: куча — 75 % лимита, остальное остаётся метаданным классов,
  потокам и буферам JVM.
- Образ и `run.sh` запускают JVM с `-XX:+ExitOnOutOfMemoryError`: первая `OutOfMemoryError` завершает процесс
  с кодом 3.
- Код 3 оставлен JVM; прогон, остановленный другим прогоном ([ADR-0014](0014-run-lock.md)), завершается с кодом 4.

## Обоснование

- Лимит следует за деревом, а не за машиной: 1 ГиБ даёт кучу 768 МиБ, около 600 000 файлов по замеру, какой бы ни была
  память хоста.
- После `OutOfMemoryError` нельзя доверять тому, что какой-либо поток довёл свою работу до конца, поэтому завершение
  процесса — единственный безопасный исход; следующий прогон продолжит прерванные загрузки
  ([ADR-0005](0005-part-file-download.md)).
- Собственный код говорит планировщику, что нужно поднять лимит, а не что отказали сайт или сеть. Это код, который
  использует `-XX:+ExitOnOutOfMemoryError` (проверено на JDK 11, 17, 21 и 25), поэтому загрузчик не возвращает его
  ни по какой другой причине.
- Работа прогона — в основном ожидание сети 4 потоками ([ADR-0004](0004-bounded-executor.md)); лимит процессоров
  не даёт прогону конкурировать с остальной машиной.

## Последствия

- Слишком большое для лимита дерево завершается с кодом 3; `ETSIORG_MEMORY` поднимает лимит, `ETSIORG_CPUS` меняет
  число процессоров.
- `run.sh` не задаёт лимита: куча — значение JVM по умолчанию, четверть памяти машины; `-Xmx` задаёт другую.
- Число файлов, которое допускает лимит по умолчанию, — оценка по синтетическому дереву: память на файл зависит
  от длины его пути.
