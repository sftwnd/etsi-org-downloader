# ADR-0012: Сборка и тесты каждого изменения в GitHub Actions

- Статус: Принято
- Дата: 2026-10-30
- Версия на английском: [ADR-0012](../0012-continuous-integration.md)

## Контекст

В репозитории не было непрерывной интеграции (#67): push и pull request никто не собирал и не тестировал. Тесты
выполнялись только там, где их кто-то запускал, а этап сборки образа Docker выполнял `./mvnw verify` со всеми тестами —
около минуты на каждую сборку образа. Тесты шли только на JDK 11, хотя `run.sh` запускает jar той JDK, что указана
в `JAVA_HOME` или найдена в `PATH`, а `maven.compiler.source` и `target` 11 не мешают более новому javac компилировать
против API своей JDK.

## Решение

- Workflow `.github/workflows/build.yml` запускается на push в `master` и `develop`, на pull request и вручную,
  как в `crayfish-common-crc`:
  - `build` — `./mvnw -B -ntp verify`, модульные тесты и `ModulePathIT` ([ADR-0011](0011-jpms-module.md)),
    на Temurin JDK 11, 17, 21 и 25: уровень языка и среда выполнения образа, а также более новые LTS-версии,
    которыми `run.sh` может запустить jar;
  - `docker` — `docker compose build` и запуск сервиса с неверной конфигурацией: код завершения 2
    ([ADR-0008](0008-error-isolation-exit-code.md)) показывает, что JVM, jar и конфигурация журнала образа
    запускаются.
- Workflow только читает репозиторий и не сохраняет токен checkout; новый push в pull request отменяет прогон
  для предыдущего.
- `pom.xml` задаёт `maven.compiler.release` 11 вместо `maven.compiler.source` и `target`.
- Этап сборки образа собирает jar без тестов (`-Dmaven.test.skip=true`).
- Pull request вливается после того, как его проверки прошли.

## Обоснование

- Каждое изменение собирается и тестируется до слияния, а pull request показывает результат.
- Матрица ловит то, что работает только на одной JDK: тесты, module path, запуск обоих jar. LTS-версии — это те JDK,
  которыми пользователь скорее всего запустит `run.sh`.
- `--release 11` уравнивает сборки матрицы: javac любой JDK проверяет код по API Java 11, а `source` и `target`
  проверяют только уровень языка и версию class-файлов.
- Образ собирается из исходников, которые workflow уже проверил, поэтому тесты не повторяются в каждой сборке образа.
- Запуск с неверной конфигурацией не требует сети: проверка не зависит от www.etsi.org и не нагружает его.

## Последствия

- `docker compose up --build` не запускает тесты: локально их запускает `./mvnw verify`.
- Каждый push запускает четыре сборки проекта и одну сборку образа.
- Новые JDK предупреждают о том, что собираются запретить: на JDK 21 и 25 Mockito динамически загружает свой агент,
  на JDK 25 Lombok вызывает `sun.misc.Unsafe`. Предупреждения не ломают сборку; матрица покажет, когда они станут
  ошибками.
