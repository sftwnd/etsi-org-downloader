# ADR-0003: HTTP-доступ — HttpURLConnection с таймаутами и повторами

- Статус: Принято
- Дата: 2026-10-30
- Версия на английском: [ADR-0003](../0003-http-timeouts-retries.md)

## Контекст

`Page` открывал `HttpURLConnection` с настройками по умолчанию (#11):

- `connectTimeout` и `readTimeout` равны `0` — ожидание без ограничения: одно зависшее соединение блокировало прогон
  навсегда;
- 5xx, 429 и сетевые сбои не повторялись;
- при ответе не 200/206 соединение не освобождалось, поле `connection` оставалось заполненным при `inputStream == null`,
  что давало NPE при следующем обращении;
- чтение листинга не обрабатывало конец потока, а текст декодировался кодировкой платформы.

Обход `/deliver/` — это сотни тысяч запросов за многочасовой прогон, поэтому сбои сети и сервера — штатная ситуация.
www.etsi.org сейчас обслуживается через Cloudflare (`server: cloudflare`): листинги приходят с
`Content-Type: text/html; charset=UTF-8`, файлы — с `Accept-Ranges: bytes`, `Last-Modified` и `ETag`.

## Решение

Остаться на `HttpURLConnection` и добавить в `Page`:

- `HttpSettings` — таймаут соединения 30 с, таймаут ожидания данных 60 с, 3 попытки, задержка перед второй попыткой
  1 с, перед каждой следующей — вдвое больше;
- повтор при сетевой ошибке и ответах `408`, `429`, `5xx`; если сервер прислал `Retry-After` в секундах и он больше
  расчётной задержки, используется он, но не больше минуты; остальные ответы — окончательная ошибка;
- поля страницы меняются только при успешном открытии; при ошибке поток ответа и соединение освобождаются;
  `disconnect()` позволяет явно освободить соединение;
- `charset()` — кодировка из `Content-Type`, по умолчанию UTF-8;
- листинг читается через `readNBytes`, ранний конец потока — `EOFException`;
- ошибка чтения во время скачивания файла продолжает загрузку с текущего смещения через новое соединение
  (тот же механизм, что и при преждевременном конце потока).

## Обоснование

- `HttpURLConnection.setReadTimeout` ограничивает каждое чтение, поэтому зависание на середине большого файла
  обнаруживается. В Java 11 таймаут запроса `java.net.http.HttpClient` действует только до получения заголовков ответа,
  чтение тела им не ограничивается. Переход дал бы перестройку `Page` и тестов без выигрыша в надёжности.
- Повторяются только сбои, которые могут пройти сами: сетевые ошибки, перегрузка (`429`, `503`) и ошибки сервера.
  `404` и другие клиентские ошибки при повторе не изменятся.
- Экспоненциальная задержка и `Retry-After` снижают нагрузку на сайт при сбоях. Верхняя граница в минуту не даёт одному
  ресурсу надолго занять поток: ресурс, который не удалось получить, будет взят в следующем прогоне.
- Значения таймаутов выбраны с запасом для больших файлов и медленных каналов; они собраны в `HttpSettings`,
  поэтому тесты используют короткие значения, а изменение по умолчанию затрагивает одно место.

## Последствия

- Прогон больше не зависает на одном соединении: в худшем случае ресурс даёт ошибку после трёх попыток.
- Ожидание перед повтором занимает поток пула; при трёх попытках это не больше нескольких секунд, при `Retry-After` —
  до минуты.
- Ошибка чтения тела листинга не повторяется внутри прогона: листинги небольшие, такой листинг будет обработан
  при следующем запуске.
